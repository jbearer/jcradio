The best fit is to keep VS Code local and give Copilot a small SSH command surface. Do not use Remote-SSH for this phase: it needs to install a VS Code server on the Pi, while ordinary SSH can inspect the machine without changing its software.

Your existing Raspberry Pi recovery notes already describe the right inventory areas and preservation rules. I would structure the setup like this.

**1. Use an SSH alias with connection reuse**

On your local machine, add an entry to `~/.ssh/config`:

```sshconfig
Host jcradio-pi
    HostName 192.168.x.x
    Port 22
    User pi
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes

    ControlMaster auto
    ControlPersist 10m
    ControlPath ~/.ssh/controlmasters/%C

    ServerAliveInterval 30
    ServerAliveCountMax 3
    ForwardAgent no
    RequestTTY no
```

Create the local control-socket directory:

```sh
mkdir -p ~/.ssh/controlmasters
chmod 700 ~/.ssh/controlmasters
```

Use the Pi’s current LAN address, not the historical DDNS address or port from the documentation until you verify those are still relevant.

With this configuration, each command can be invoked normally:

```sh
ssh jcradio-pi 'uname -a'
ssh jcradio-pi 'cat /etc/os-release'
ssh jcradio-pi 'dpkg-query -W'
```

The first command establishes the SSH connection; subsequent commands reuse it for ten minutes. This gives Copilot multiple independent commands without repeated authentication or a VS Code server.

**2. Give Copilot an explicit operating rule**

A useful instruction for this phase is:

> Use the SSH alias `jcradio-pi` for Raspberry Pi inspection. Use non-interactive SSH commands where possible. Do not use `sudo`, `apt`, `apt-get`, package managers, service restarts, reboot/shutdown commands, database tasks, or commands that write files. Do not copy secrets into chat or the repository. Treat the Pi as read-only until explicitly approved.

This is a workflow guard, not a technical security boundary. If you need hard enforcement, the SSH account itself would need restricted permissions or a forced command, which would require changing the Pi.

**3. Capture one local inventory**

Run a single read-only collection and save the result locally:

```sh
snapshot="docs/pi/snapshots/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$snapshot"

ssh jcradio-pi '
set +e

section() {
    printf "\n===== %s =====\n" "$1"
}

section "identity"
hostname
id
date
uptime

section "os-and-hardware"
uname -a
cat /etc/os-release
cat /proc/device-tree/model 2>/dev/null
getconf LONG_BIT
dpkg --print-architecture

section "storage-and-memory"
df -hT
free -h 2>/dev/null
mount

section "installed-debian-packages"
dpkg-query -W -f="${binary:Package}\t${Version}\n"

section "manually-installed-packages"
apt-mark showmanual 2>/dev/null

section "available-runtimes"
for name in ruby bundle rails gem python python3 pip pip3 node npm git gcc make ffmpeg librespot icecast2 nginx apache2; do
    printf "\n-- %s --\n" "$name"
    command -v "$name"
    "$name" --version 2>&1
done

section "ruby-gems"
gem list --local 2>/dev/null

section "python-packages"
python3 -m pip list 2>/dev/null

section "running-processes"
ps auxww

section "listening-sockets"
if command -v ss >/dev/null 2>&1; then
    ss -lntup
elif command -v netstat >/dev/null 2>&1; then
    netstat -lntup
fi

section "services"
systemctl list-unit-files --type=service --no-pager 2>&1
systemctl list-units --type=service --all --no-pager 2>&1

section "scheduled-jobs"
cat /etc/crontab 2>/dev/null
find /etc/cron.d /etc/cron.daily /etc/cron.hourly /etc/cron.weekly /etc/cron.monthly \
    -maxdepth 1 -type f -print 2>/dev/null

section "historical-launch-commands"
for name in jcradio-start jcradio-stop librespot-start; do
    printf "\n-- %s --\n" "$name"
    command -V "$name" 2>&1
done

section "project-checkout"
if [ -d "$HOME/jcradio/.git" ]; then
    cd "$HOME/jcradio"
    git rev-parse --show-toplevel
    git rev-parse HEAD
    git status --short --branch
fi
' > "$snapshot/host-inventory.txt"

chmod 600 "$snapshot/host-inventory.txt"
printf 'Saved %s\n' "$snapshot/host-inventory.txt"
```

This inventories Debian packages, language runtimes, gems, processes, sockets, services, cron jobs, launch commands, and the repository state. It intentionally does not dump environment variables, secrets, service files, OAuth configuration, private keys, or application databases.

Keep the generated snapshot outside normal commits, or add the snapshot directory to a local-only ignore rule. The existing Pi file-copy notes are a good place to record selected redacted configuration files later.

**4. For a genuinely interactive shell**

When a persistent shell is useful, start one separately:

```sh
ssh -tt jcradio-pi 'HISTFILE=/dev/null exec bash --noprofile --norc'
```

Copilot can then continue using that terminal session for several exploratory commands. This is more convenient, but it is also easier to lose track of whether a command changed state, so I would use it only after the initial inventory and with the read-only rule above.

**5. Preserve the Pi beyond an inventory**

A command transcript is not a complete time capsule. If you have physical access and need bit-for-bit preservation, the strongest option is to power the Pi down and make an image of the SD card from another Linux machine, then hash the image. That does not modify the Pi, but it does require downtime and careful identification of the correct block device.

If you cannot image it yet, avoid casually copying a live SQLite database. The project notes correctly call for SQLite’s online backup mechanism or a clean stop before preserving database files. Also remember that simply logging in can update SSH/login logs, so “completely untouched” and “remotely inspected” are not perfectly compatible.

I would use this order:

1. Verify the Pi’s SSH host key and connect through `jcradio-pi`.
2. Capture the inventory above.
3. Inspect launch scripts, service definitions, and the checkout privately, redacting secrets.
4. Preserve the SD card or application data before any repair.
5. Only then consider a local clone, `rsync`, or future changes.

This avoids the VS Code Server compatibility problem while still giving Copilot a fast, repeatable way to understand the old installation.
